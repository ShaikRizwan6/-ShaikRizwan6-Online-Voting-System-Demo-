Technical Whitepaper

Online Voting System Architecture

A production-ready reference application demonstrating full-stack engineering, transaction isolation, and secure balloting.

Architectural Core

The Online Voting System is built as a stateful client-server architecture utilizing Node.js LTS (CommonJS), Express.js, and MySQL 8 (InnoDB). The user interface is cleanly served from the public directory as a responsive Single Page Architecture powered by Bootstrap 5, Vanilla JavaScript, and Chart.js.

Layer Technology Key Responsibility
Presentation Layer HTML5, Bootstrap 5, Chart.js Responsive dashboards, interactive ballot selection, live statistical charts.
Client Communication Native Fetch API JSON payloads, automatic CSRF token transmission via X-CSRF-Token header.
Server Layer Node.js & Express.js REST routing, role verification middleware, rate limiting, and centralized error handling.
Database Layer MySQL 8 (InnoDB) ACID transaction isolation, composite unique constraint enforcement, cascade relational integrity.

ACID Transactional Voting Engine

The ballot submission handler (POST /api/elections/:id/vote) enforces uncompromising atomicity and data consistency:

  1. Transaction Initialization: Acquires a dedicated database client connection from the MySQL pool and initiates START TRANSACTION.
  2. Row Locking & Eligibility Verification: Uses SELECT ... FOR UPDATE to inspect voter active status and ensure the election is strictly in published status within valid start/end datetime boundaries.
  3. Engine-Level Uniqueness: Executes INSERT INTO votes (election_id, voter_id, candidate_id). The composite unique index (election_id, voter_id) makes it physically impossible for any race condition to register a duplicate vote.
  4. Graceful Conflict Handling: Trapping MySQL error ER_DUP_ENTRY (code 1062) triggers an instant ROLLBACK and returns an HTTP 409 Conflict status with a friendly voter advisory.
  5. Commit: Successful balloting triggers COMMIT and releases the pooled connection back to the MySQL pool in a mandatory finally block.

Enterprise Security Controls

Bcrypt Cryptographic Hashing

Plaintext credentials never touch disk. All passwords are salted and hashed using 10 bcrypt computational rounds.

Session Fixation Protection

Upon successful authentication, the server regenerates the session ID to neutralize fixation attacks.

CSRF Token Validation

Double-submit session-backed CSRF tokens validate every state-mutating request (POST, PUT, PATCH, DELETE).

Rate Limiting Protection

The authentication endpoint is protected by an in-memory sliding window limiter to prevent automated password cracking.

Placement Interview Talking Points

Double-voting prevention is not delegated to the frontend or application memory. It is enforced simultaneously at two levels: (1) Application row locks using SELECT FOR UPDATE within a MySQL transaction, and (2) Database engine level via InnoDB's composite unique key UNIQUE KEY unique_vote (election_id, voter_id). Any parallel attempt is rejected by the database engine and safely caught as an ER_DUP_ENTRY error.

Voting systems require strict ACID (Atomicity, Consistency, Isolation, Durability) properties. Without transactions, unexpected server crashes, network disruptions, or concurrent requests could result in orphaned records, inaccurate tallies, or voters being marked as voted without their ballot successfully being counted.

Client-side UI states are purely visual conveniences. Server-side middleware (middleware/auth.js and middleware/admin.js) intercepts every single API request, validating the session metadata stored securely in MySQL-backed sessions. Any non-admin attempting to access /api/admin/* receives a 403 Forbidden response.
